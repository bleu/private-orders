## Compatibility with CowAuthWrapper

### Coexistence is possible, but authentication does not transfer automatically

**READ**. Independent deployments can coexist. In one wrapper chain, an auth wrapper can be outside the private wrapper, provided the concrete auth implementation continues through `_next`, all required callers are authenticated, and the private wrapper remains last. Execution is outer-auth prelogic, private prelogic, settlement, private postlogic, outer-auth postlogic. LAST means no wrapper inside the private wrapper; it does not prohibit an outer wrapper's post-settlement code (`src/PrivateTradeWrapper.sol:135-147`; `template/src/CowAuthWrapper.sol:135-142`; `template/src/CowWrapper.sol:197-227`). The contrary blanket statement about post-settlement composition in `docs/DESIGN.md:220-223` is too broad.

**READ**. This is not a plug-in chain for the current bytes. Auth `_wrap` expects `nestedAppData[32] | orderData[384] | signature[65] | wrapperParams`, whereas the private wrapper expects ABI-encoded `(declaredOfferId, terms, proposal)` (`template/src/CowAuthWrapper.sol:128-136`; `src/PrivateTradeWrapper.sol:167-168`). Auth requires the order's appData to equal the envelope hash (`template/src/CowAuthWrapper.sol:160-164`). The existing builder instead uses a JSON document hash (`src/libraries/PrivateTradeAppData.sol:68-70`). The private handler permits a different appData so long as the order hash and other terms validate, and the private wrapper requires the two legs' appData to agree (`src/PrivateTradeOrder.sol:148-166`; `src/PrivateTradeWrapper.sol:340-344`).

**READ**. An extra unrelated auth-owned order cannot simply be added to this settlement; the private wrapper requires exactly two trades and the two expected owners (`src/PrivateTradeWrapper.sol:333-334,347-371`). Authenticating an existing private-trade leg through an outer wrapper is conceptually different from adding a third trade.

### What GPv2 actually calls for Shed-owned orders

**READ**. The exact call path is:

### Concrete adoption changes

**SUSPECTED**. There are two sensible port designs. Retaining Shed ownership and adding an auth check to the conditional handler preserves more of this repository. Moving order ownership to the wrapper requires a different custody and funding design. Neither has been implemented or tested here.

1. **READ. Make authentication part of actual validation.** With Shed ownership retained, a new handler can preserve existing checks and additionally call the auth wrapper's `isValidSignature` for the GPv2 digest. Alternatively, a new Shed implementation can forward validation there, but would also need an explicit plan for the existing conditional authorization checks. A normal external call must read the auth wrapper's storage context; merely changing `_settlementOrderOwner` does not do that. Evidence is the call path above and the contract-local `tstore`/`tload` in `template/src/CowAuthWrapper.sol:183-188,345-352`.
2. **READ. Authorize both parties and define the pair envelope.** Implement `_authorizingOwner`, `_wrapperSigningData`, `_authedWrap`, `name`, and deterministic `validateWrapperData`. Each base invocation commits only one order; `_commitOrder` is private (`template/src/CowAuthWrapper.sol:124-159,221-248`). A bilateral port needs two authorized order commitments, either through two outer auth invocations or an explicitly adapted pair implementation. If role-specific params produce different envelope hashes, the current equal-appData rule must change; alternatively define one common pair envelope with independently authorized order digests. Signing one party's order does not establish the other party's authorization.
3. **READ. Port the wrapper body rather than stacking inheritance.** Both concrete `_wrap` implementations are non-virtual (`src/PrivateTradeWrapper.sol:131-134`; `template/src/CowAuthWrapper.sol:124-127`). A new implementation must move private-trade checks and lifecycle into the auth base's `_authedWrap` flow, or retain the old private wrapper behind separate auth layers. Preserve LAST while relying on calldata price/shape checks. Preserve both UID fill checks; the template checks only its one committed order (`:135-142`).
4. **READ. Change signing, encoding, and service integration.** Define canonical EIP-712 pair types and wrapper-domain signatures; update builders, typed-data rendering, payloads, appData computation, and orderbook registration. The envelope avoids JSON self-reference by hashing a nested document without this wrapper's call (`template/README.md:15-25`; `template/src/CowAuthWrapper.sol:97-109,203-218`). It is not the ordinary JSON hash currently emitted. The new ERC-165 capability advertises getters to backends (`:49-61,112-117`), but source advertisement is not proof that the deployed orderbook/driver supports this format. Safe-owned authorization needs particular care: the base accepts a fixed 65-byte ECDSA signature or an on-chain preapproval, not an arbitrary ERC-1271 signature blob (`:128-132,173-180`). Existing Shed bundle signing supports contract owners (`src/libraries/ShedBundle.sol:297-310`), so a port must preserve that capability or deliberately use preapproval.
5. **READ. Redeploy and re-establish lifecycle/configuration.** Existing deployed immutable contracts cannot be converted. New bytecode and dependent constructor inputs change CREATE2 predictions (`src/libraries/PrivateTradeDeployment.sol:47-52`). Retaining Sheds retains their token-source role. Defaulting the order owner to the auth wrapper instead makes GPv2 pull from that wrapper, so funding, approvals, receiver checks, UID tracking, and cancellation must move accordingly (`template/src/CowAuthWrapper.sol:250-267`; `GPv2Settlement.sol:433-438`). New deployment verification and the relevant allowlist approvals are still required.
